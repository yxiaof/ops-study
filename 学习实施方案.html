🧩 举一反三：3 道变式题（先自己做，再看操作要点）

题 1（高频事故）：某服务写不了日志，排查发现 /var/log 所在盘满了。要求：安全清理——不许直接 rm 正在被写入的日志文件（rm 了空间也不会释放）。怎么定位、怎么清？

提示：想想"文件被删除但进程还开着"会怎样。

操作要点
① df -h 确认哪个盘满 → du -sh /* 2>/dev/null | sort -rh | head 找目录；② 找"已删未释放"的句柄：lsof +L1（在你的 ECS 上直接执行）；③ 安全清理：truncate -s 0 文件名 或 : > 文件名 清空而不是删除；④ 根治：配 logrotate 做轮转+保留策略。

题 2：找出你电脑上最近 24 小时内被修改过的所有 .conf / .ini 配置文件（比如排查"谁改了配置"）。

操作要点
find ~ -name "*.conf" -mtime -1 2>/dev/null；更精确用时间戳：find ~ -name "*.conf" -newermt "24 hours ago"。延伸：加 -ls 看修改时间与大小，配合 diff 对比备份判断改了什么。

题 3：本机 8080 端口被一个"不知道哪来的"进程占用，服务起不来。找出它并安全停掉。

操作要点
在 ECS 上：ss -tlnp | grep 8080 或 lsof -i:8080 直接看到进程名和 PID → kill PID。本机 Windows 对照：netstat -ano | findstr :8080 + taskkill /PID xxx。安全原则：先确认是什么进程（别误杀关键服务）再停。

❓ 面试官追问链："服务器负载很高怎么排查？➜ load 高但 CPU 空闲，什么原因？（IO 等待）➜ 怎么确认是哪块盘/哪个进程在等？"

参考答案要点（先自己想，再点开对照）
① 按"四类瓶颈"逐项排除：uptime 看 load → top 看 us/sy/wa 占比与最耗资源进程 → free/swap 看内存（si/so 频繁=内存吃紧）→ iostat -x 看 %util → ss/tcpdump 看网络。
② load 高但 CPU 空闲 = 大概率 iowait 高（top 的 wa 列大），IO 队列长或大量 D 状态（不可中断睡眠）进程。
③ iostat -x 找 %util 最高的盘 → iotop -o 定位进程 → pidstat -d 确认该进程读写量 → 再深挖（RAID 降级、NFS 抖动也算 IO 问题）。
加分项：说出 USE 方法（利用率/饱和度/错误）或"先定位瓶颈类型再深挖"的方法论。
  • 达标：10 分钟说清陌生机器的负载与瓶颈；5 分钟定位"服务起不来"

# ① 建脚本（先写最简版：磁盘+内存检查）
cd ~/lab && cat > env_check.sh <<'EOF'
#!/usr/bin/env bash
set -euo pipefail
DISK_THRESHOLD=85

echo "==== 环境巡检 $(date '+%F %T') ===="

# 磁盘检查
du_pct=$(df / | awk 'NR==2{gsub("%","",$5); print $5}')
if [ "$du_pct" -gt "$DISK_THRESHOLD" ]; then
  echo "[WARN] C盘使用率 ${du_pct}% 超过阈值 ${DISK_THRESHOLD}%"
else
  echo "[OK]   C盘使用率 ${du_pct}%"
fi

# 关键进程检查（以 nginx 容器为例，没有就显示 MISS）
if docker ps --format '{{.Names}}' 2>/dev/null | grep -q nginx; then
  echo "[OK]   nginx 容器在运行"
else
  echo "[MISS] 未发现 nginx 容器（技能 3 会装）"
fi

exit 0
EOF

# ② 语法检查（把脚本内容贴到 shellcheck.net，或本地装 shellcheck）
bash -n env_check.sh        # 语法检查
# ③ 加执行权限并运行
chmod +x env_check.sh && ./env_check.sh
# ④ 退出码验证（自动化依赖它）
echo "exit code: $?"

✅ 验收：脚本输出带 [OK]/[WARN] 的报告；把阈值改成 1 能触发 WARN；shellcheck 无 error。

  listen 443 ssl;

# ④ 看一次完整握手过程（关键：SSL certificate verify result）
curl -kv https://localhost:8443 2>&1 | grep -E "SSL|subject|issuer" | head -8

# ⑤ 亲手制造 502：把后端"弄死"
docker run -d --name upstream -p 9000:80 nginx:1.27-alpine
cat > proxy.conf <<'EOF'
server {
  listen 80;
  location / { proxy_pass http://host.docker.internal:9000; }
}
EOF
docker run -d --name proxy -p 8082:80 --add-host=host.docker.internal:host-gateway \
  -v /root/lab/tls/proxy.conf:/etc/nginx/conf.d/default.conf:ro nginx:1.27-alpine
curl -i http://localhost:8082 | head -5        # 200：通
docker stop upstream
curl -i http://localhost:8082 | head -5        # 502！后端没了

# ⑥ 对比 504：反代到一个"没人接的黑洞"地址（超时型）
sed -i 's|host.docker.internal:9000|10.255.255.1:9000|' ~/lab/tls/proxy.conf
docker restart proxy && curl -i --max-time 15 http://localhost:8082 | head -5   # 504

import csv, socket, time

def check(host, port, timeout=2):
    start = time.perf_counter()
    try:
        with socket.create_connection((host, int(port)), timeout=timeout):
            return True, round((time.perf_counter() - start) * 1000)
    except OSError:
        return False, round((time.perf_counter() - start) * 1000)

def main():
    rows, ok = [], 0
    with open("hosts.csv", newline="", encoding="utf-8") as f:
        for host, port in csv.reader(f):
            reachable, ms = check(host, port)
            ok += reachable
            rows.append(f"[{'OK' if reachable else 'FAIL'}] {host}:{port}  {ms}ms")
    print("\n".join(rows))
    print(f"---- {ok}/{len(rows)} 可达 ----")

if __name__ == "__main__":
    main()
EOF

3.1 三个 STAR 故事模板（面试前必须备好）

STAR = 情境 Situation → 任务 Task → 行动 Action → 结果 Result。三个故事覆盖 90% 的行为面问题：

故事一：故障复盘故事（对应"讲一次印象最深的故障"，SRE 面必问）

S：什么业务、什么故障、影响多大（量化：影响用户数/时长/资损）
T：你在其中的角色（发现者/止损者/复盘 owner）
A：按时间线讲动作——怎么发现的（监控/告警）→ 怎么定位（用了什么工具、排除法过程）→ 怎么止损（回滚/降级/切换的决策点）
R：多久恢复 + 复盘产出（改进项 N 条、防复发机制、Runbook 沉淀）

要点：时间线必须顺、必须有"决策点"（为什么选回滚而不是排查）、结尾必须闭环到防复发——没有改进项的故障故事 = 减分项。素材来源：底座 7 监控实战 + SRE 方向达标作业的模拟故障演习。

  • 写好并口头演练过一次完整的故障故事（3 分钟版）

故事二：自动化提效故事（对应"你做过什么有价值的事"）

S：手工痛点量化（"20 台机器巡检要 2 小时、还常漏检"）
T：目标（全自动 + 报告 + 告警）
A：方案与技术栈（Python + paramiko + …，讲一个技术难点怎么解决）
R：结果量化（2 小时 → 5 分钟、错误率 0、团队 N 人复用）

素材来源：底座 5 Python 批量巡检工具、底座 11 AI 辅助开发案例。

  • 写好并演练过自动化故事（含量化数字）

故事三：跨团队推动故事（对应 61% 的沟通协作要求）

S：跨团队僵局场景（研发说代码没问题、运维说环境没问题）
T：你作为推动者要拿到结论
A：沟通动作——拉齐数据（全链路追踪证据）、组织方案评审、明确责任边界
R：问题闭环 + 沉淀机制（以后同类问题怎么避免扯皮）

素材来源：底座 7 链路追踪练习（用调用链数据说话就是最好的跨团队沟通案例）。

  • 写好并演练过跨团队推动故事

3.2 On-Call 应急走位（48% 岗位要求的硬流程）

告警响起 60 秒内三问：① 影响面多大（哪些业务/用户）？② 最近 24h 有什么变更？③ 能不能直接回滚？
铁律：止损优先于根因——先恢复业务，再查原因（面试官最爱考这个优先级）
止损三选一决策：回滚（有变更）→ 降级/限流（容量问题）→ 切换（主备/多活）
通报模板：现状（什么坏了）+ 影响（谁受影响）+ 动作（正在做什么）+ 预期（预计多久恢复）——每 30 分钟同步一次
事后：24-48h 内出复盘报告（用故事一的结构）
  • 能口述完整应急走位，并独立写出一份通报模板

3.3 系统设计题卡（高级岗必考，白板讲 5 分钟）

题目答题框架（按层展开）
设计一个监控体系分层（基础设施/容器/应用/业务指标）→ 指标选型（每层 3-5 个核心指标）→ 告警分级（P0-P3 与响应时限）→ 数据保留与容量 → 用混沌演练验证告警有效性
